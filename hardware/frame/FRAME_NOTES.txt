Frame Glasses Notes
===================

Why use Frame
-------------
- Replace our custom display board and custom mic BLE peripheral with one programmable wearable.
- Keep the phone as the host for speech recognition, translation, networking, and app UI.
- Use Frame as the main peripheral for:
  - microphone capture
  - text and bitmap display
  - lightweight on-device logic in Lua
  - saved device-side preferences


High-value ideas for HUDini on Frame
------------------------------------
1. Live caption HUD
- Stream microphone audio from Frame to the phone.
- Run transcription + translation on the phone.
- Send translated text back to Frame for display.
- Show partial captions and final captions differently.

2. Customizable display preferences
- Let the app set:
  - transcription color
  - translation color
  - brightness
  - caption position
  - layout mode
  - live partials on/off
- Save those preferences on Frame so they persist after reconnect/reboot.

3. Suggested replies on-glasses
- Show 2-3 short suggested responses.
- Optionally show phonetic pronunciation under the suggested reply.
- Use a tap/gesture or host command to cycle suggestions.

4. Conversation modes
- Translation mode
- Transcription-only mode
- Meeting / lecture mode
- Pronunciation coach mode
- The phone app can switch modes; Frame only needs to render the correct UI and stream mic audio.

5. Better connection UX
- On-device states such as:
  - disconnected
  - listening
  - translating
  - muted
  - error / reconnecting
- This is much cleaner than our current text-only ESP32 status path.

6. Future expansion
- Because Frame is a broader platform, we have a path to add:
  - richer HUD layouts
  - bitmap icons / status indicators
  - camera-driven features later if needed
  - more on-device interaction logic without redesigning custom hardware


Recommended architecture
------------------------
- iPhone app remains the BLE central and main application host.
- Frame remains the BLE peripheral.
- A small Lua app runs on Frame.
- The Frame Lua app should:
  - start/stop the microphone
  - send raw PCM chunks to the phone
  - receive display / settings messages from the phone
  - render text to the display
  - save and load preferences from the filesystem

Do not treat Frame like our current custom HUD peripheral.
Instead, add a separate "Frame transport" path in the app.


How we would program Frame
--------------------------
1. During development
- Use AR Studio / VSCode or the official SDK workflow to push Lua files to Frame.
- Iterate on a Frame-side app such as main.lua.

2. In the product flow
- The phone app connects over BLE.
- If needed, it uploads or refreshes the Lua files on Frame.
- It starts the Frame app by executing Lua / require().
- After that, the app and Frame exchange messages over BLE.

3. Preference persistence
- Store settings in a small file on Frame.
- Load settings at startup from main.lua.
- Update the file only when settings actually change.


Implementation notes for our project
------------------------------------
- Our current app assumes a custom BLE service and custom audio packet format.
- Frame uses its own BLE service and characteristics, plus Lua / raw-byte messaging.
- Our current display firmware should not be ported directly; replace it with Frame display logic.
- Our current mic firmware should not be ported directly; replace it with Frame microphone APIs.
- The speech recognition / translation pipeline on the phone can mostly stay.

Specific programming facts we will need
---------------------------------------
- Frame BLE service UUID:
  7A230001-5475-A6A4-654C-8431F6AD49C4
- TX characteristic UUID:
  7A230002-5475-A6A4-654C-8431F6AD49C4
- RX characteristic UUID:
  7A230003-5475-A6A4-654C-8431F6AD49C4

- Display:
  - frame.display.text(...)
  - frame.display.bitmap(...)
  - frame.display.show()
  - frame.display.set_brightness(...)

- BLE / host communication:
  - send Lua strings on TX
  - enable notifications on RX
  - send raw byte payloads with 0x01 prefix
  - use frame.bluetooth.receive_callback() on Frame
  - use 0x03 as break and 0x04 as reset when needed

- Persistence:
  - use the Lua filesystem APIs to save settings files
  - load those settings from main.lua on startup
